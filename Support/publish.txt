Sass Nova Extension: development and publishing
================================================

Project layout
--------------

extension.json
    Extension metadata, permissions, entry point, version, and workspace settings.

Scripts/main.js
    Activates the extension, registers save and manual compilation commands,
    and refreshes Issues when the deprecation display preference changes.

Scripts/SassService.js
    Builds the Dart Sass command, runs it, publishes located diagnostics to
    Issues, reports errors, migrates checkbox preferences, and removes a UTF-8 BOM
    from CSS files reported as generated when the run exits successfully.

Scripts/SassService.min.js
    An old minified copy. It is not loaded by extension.json or main.js, so Nova
    does not execute it. SassService.js is the maintained source of truth.

README.md, CHANGELOG.md, LICENSE, extension.png, extension@2x.png
    Extension Library documentation, release notes, licence, and icon.

Support/
    Development fixtures, retained generated output, and icon assets. The active
    icon source is extension-icon-source.png; the 3D alternatives are not active.

There is no build or minification step. Run `node Support/tests.cjs` for the
regression suite (requires Node.js and Dart Sass). It uses mocked Nova APIs and
real Sass compilation in disposable temporary directories, not the live fixtures.
Nova loads Scripts/main.js and its unminified SassService.js dependency directly.
Do not regenerate the unused minified file as part of release preparation.

Prerequisites
-------------

1. Install Nova and sign in to a Nova extension developer account.
2. In Nova > Settings > General, enable "Show extension development items in the
   Extensions Menu".
3. Install Dart Sass. For example, with Homebrew:

       brew install sass/sass/sass

4. Confirm that Sass is available:

       sass --version

Development and testing
-----------------------

1. Open Sass.novaextension as a project in Nova.
2. Choose Extensions > Activate Project as Extension.
3. Open a separate local test project OUTSIDE the .novaextension bundle. In that
   project, open Project > Project Settings > Languages & Extensions > Sass and check the
   workspace settings. Avoid running an installed copy and a development copy
   simultaneously when checking for duplicate compilation or notifications.
4. Copy fixtures into that separate test project, retaining Support/ if using
   the example paths below. Save
   Support/master.scss and Support/alternative.sass with blank Update Path and
   Output Path settings to test directory compilation. To isolate an entry point,
   set Update Path to Support/master.scss and leave Output Path blank.
   Confirm the first save compiles the latest contents. Use indented syntax
   (not SCSS braces) when editing alternative.sass.
5. Use Nova's Debug sidebar > Extension Console to inspect logs and exceptions.
6. After changing JavaScript, deactivate and reactivate the project extension if
   Nova does not reload it automatically.
7. Choose Extensions > Deactivate Project as Extension when finished.

Do not test saves inside the activated extension bundle: development auto-reload
can restart the extension after a file changes and clear its Issues collection.
This can make diagnostics briefly appear and disappear. Test in a separate
project, keeping the extension project open for editing/activation only.

Remote Projects are intentionally unsupported. When Nova identifies an editor's
document as remote, the extension displays one notification and does not register
its compile-on-save listener. Test this guard separately if remote project access is
available. This is a per-document guard, not a workspace-wide disable switch:
local documents remain eligible. The supported deployment workflow is a Local Project with Nova
Publishing configured to upload the generated CSS.

Relative-path testing
---------------------

"Resolve Paths Relative to Sass File" is off by default, preserving the original
workspace-root-relative behaviour. When it is enabled, test values such as `.` and
`../css` from Sass files at more than one directory depth. Confirm that each output
is written relative to the saved Sass file rather than the workspace root.

Sass installation testing
-------------------------

Open the Sass project settings and reload the Sass Executable choices. Confirm that
each detected installation displays its version and path. Select an installation
and use "Check Sass Installation" to verify "Dart Sass [version] is installed"
and the executable location. Also test an
invalid custom path and confirm that the failure notification explains the remedy.
With no saved selection, confirm that the first detected executable becomes selected.
The Check button's spinner must stop as soon as its notification appears, and
dismissing the notification must not produce a helper communication error.

The same activation can be performed with Nova's command-line tool:

    nova extension activate /absolute/path/to/Sass.novaextension

If `nova` is not on PATH, use Nova's bundled CLI, for a standard installation:

    /Applications/Nova.app/Contents/SharedSupport/nova extension validate /absolute/path/to/Sass.novaextension

Release regression checklist
----------------------------

Record the Nova version, macOS version, Dart Sass version, and results before
calling a release stable. Bundle validation is not a runtime or UI test.

- Test valid SCSS and valid indented Sass, and changes to a loaded partial.
- Confirm save-once behaviour and disabling compile on save.
- Verify the three sections: Compilation & Output, Paths, Sass Installation.
  Compile on Save is first. Both On/Off radio controls default to On; saved
  boolean preferences must migrate to the matching On/Off selection.
- Toggle Deprecation Warnings Off/On with populated Issues. Deprecations should
  hide/reappear immediately; ordinary warnings, errors, popups, and console
  diagnostics must remain unaffected.
- Check empty path placeholders and the Paths heading describe the css/scss
  defaults. Placeholders must not be saved as actual configuration values.
- Test Expanded/Compressed and all three source-map choices. None does not
  remove old map files; use clean output directories for each test.
- Test Error CSS Yes/No, a syntax error, then a successful save. Check full
  console diagnostics and that successful deprecation warnings are not errors.
- Test a non-ASCII CSS value in compressed output to exercise BOM removal.
  Test Remove UTF-8 BOM On (default) and Off: On strips the BOM, Off preserves
  it. Force a fresh output by removing only the disposable test CSS before each
  run; changing the setting alone does not rewrite existing output.
  The existing master.scss fixture is ASCII and does not exercise this case.
  Check the generated bytes are not EF BB BF and the non-ASCII text is intact.
  Cleanup only happens after successful runs for reported generated files.
- Test workspace-relative and file-relative paths, blank paths, spaces, nested
  partials, and a single-file input paired with a CSS output filename.
- Test executable selection and the Check button in Nova itself, including
  dismissing the notification and invalid paths. Mocks cannot verify the UI.
- Test a remote document and confirm local documents are still usable.
- With compile-on-save off, test Compile Now from the Extensions
  menu and Command Palette. Open a saved Sass file first. Save dirty Sass/CSS
  documents before retrying a blocked command. Verify it uses the active file's
  save scope, and test both directory and single-file Update Paths.
  The menu label is "Sass: Compile Now". Also test a single-file Update Path
  with blank Output Path: its CSS should be generated beside the input.
- Click a syntax error in an imported partial in the Issues sidebar. Fix it and
  compile again; the issue should clear. Check warnings and separate scopes too.
- Nova's built-in Files sidebar context menu is not an available extension hook;
  no right-click command is included. See https://docs.nova.app/extensions/commands/

Before publishing
-----------------

1. Review git status and make sure generated test CSS is not being released by
   accident.
2. Update the version in extension.json. The Extension Library requires an update
   to have a version newer than the currently published release.
3. Add the release notes to CHANGELOG.md and update README.md when behaviour or
   settings change.
4. Confirm extension.json contains the identifier, name, organization,
   description, repository, bugs URL, entry point, and required entitlements.
   Confirm extension.png and extension@2x.png exist in the bundle root; they
   are files, not an icon key in extension.json.
5. Validate the bundle in Nova with Extensions > Submit to the Extension Library,
   or from the command line:

       nova extension validate /absolute/path/to/Sass.novaextension

Publishing
----------

Graphical route:

1. Open Sass.novaextension as a Nova project.
2. Choose Extensions > Submit to the Extension Library.
3. Resolve any validation errors, review the submission, and submit it while signed
   in to the developer account that owns the existing extension identifier.

Command-line route:

    nova extension login
    nova extension whoami
    nova extension validate /absolute/path/to/Sass.novaextension
    nova extension publish /absolute/path/to/Sass.novaextension

After submission, check the extension's listing and release notes in the Extension
Library. The listing is built from extension.json and the bundle documentation.
